# 设计文档库

## 职责与自主权

本 Skill 只负责文档的组织、内容规范和维护。

- 开发者设计文档库记录开发者与 AI 共同确定的项目设计。
- AI 设计记录文档库记录 AI 在技术实现过程中自主确定的关键技术设计。
- 两套文档通过开发者定义的模块建立映射关系。
- 文档描述当前有效状态，Git 保存完整历史版本和 Diff。

AI 可自主分析和完善需求、设计架构、选择技术方案、设计数据结构和数据库、设计内部运行逻辑、制定实现方案、编写代码及设计和执行测试。此 Skill 不设置开发阶段、审批关卡或固定执行顺序，也不要求先写完文档才能开发。

开发者负责定义系统目标、功能和边界。AI 自主决定如何实现，并沉淀关键技术设计。技术设计涉及修改已确定的模块边界、功能行为或接口约束时，应与开发者讨论并同步更新设计文档。已有明确授权或已讨论确定的内容可以直接同步。

## 目录与导航

遵循用户指定的文档根目录。未指定时沿用项目现有文档根目录，无约定时使用 `docs/`。子项目的文档保存在其自身目录中。

采用浅层组织，示例中的“项目文档”表示实际文档根目录。

```text
项目文档/
├── index.md
├── 开发者设计文档库/
│   ├── index.md
│   ├── 总体架构设计.md
│   ├── 模块1.md
│   └── 模块2.md
└── AI设计记录文档库/
    ├── index.md
    ├── 模块1/
    │   ├── 数据结构设计.md
    │   └── 运行逻辑与时序设计.md
    ├── 模块2/
    │   └── 状态管理设计.md
    └── 跨模块设计/
        └── 模块通信与数据流设计.md
```

- 按实际内容创建文档，避免预建空文件、过度拆分和统一配齐每类技术文档。
- 总体架构和开发者模块文档平铺。AI 技术文档按同名模块分组。
- 用户指定在线文档时，保持对应的索引、模块和引用关系。
- 已有同主题文档优先更新或迁移。调整结构时同步修复引用。

| 索引 | 维护内容 |
| --- | --- |
| 文档根目录 `index.md` | 两套文档库的定位、职责边界及其索引链接 |
| 开发者设计文档库 `index.md` | 总体架构、模块设计和模块关系导航 |
| AI设计记录文档库 `index.md` | 项目模块、各模块技术文档及内容摘要、对应开发者文档、跨模块设计及涉及模块 |

索引通过链接组织内容，避免重复正文。模块或技术文档变化时同步更新索引。AI 索引可列出尚无技术文档的现有模块，无需为其创建空目录或占位文档。

## 开发者设计文档库

核心问题是系统应该做什么、应该是什么样子，以及有哪些必须遵守的约束。

| 文档 | 记录内容 |
| --- | --- |
| 总体架构设计 | 项目目标、整体架构、模块划分、职责与边界、依赖和协作关系、跨模块接口要求、全局业务约束 |
| 模块文档 | 职责与边界、功能规划及预期行为、接口要求与接口预留、必要业务流程与时序、验收标准、开发者指定的特殊技术约束、重要设计变更 |

- 记录共同确定的设计。待讨论建议明确标为待定，避免将 AI 建议或用户未回复视为确认。
- 开发者明确指定的框架、协议或其他特殊技术约束写入对应设计。
- 不主动规定具体技术实现方式，除非开发者明确提出要求。AI 自主确定且具有长期价值的实现方案归入 AI 设计记录文档库。
- 功能验收标准应能判断行为是否符合约定，包含重要失败场景。

| 变化 | 文档处理 |
| --- | --- |
| 模块增加、删除、合并、拆分或职责边界调整 | 更新总体架构、相关模块及映射 |
| 接口约定、接口预留、模块关系变化 | 更新对应模块及受影响的跨模块设计 |
| 重要功能、预期行为、业务流程、执行顺序或时序变化 | 更新对应模块设计 |
| 验收要求、全局架构或关键约束变化 | 更新相应设计及引用 |
| 普通按钮位置、颜色、间距、文字、样式调整 | 无需记录 |
| 不影响设计的 Bug 修复、普通重构、类或函数封装 | 无需记录 |

判断依据是设计影响。局部视觉或实现修改一旦改变功能行为、接口或验收要求，仍应更新相关设计。

新建或重整文档时可参考[开发者设计模板](assets/developer-design-template.md)，按总体架构或模块的实际内容裁剪。

## AI 设计记录文档库

核心问题是系统内部的关键数据如何组织、核心逻辑如何运行、各部分如何协作。

| 值得记录的设计 | 典型内容 |
| --- | --- |
| 数据组织 | 核心数据结构、数据库、数据约束和必要的迁移设计 |
| 运行机制 | 核心业务逻辑与时序、状态机、状态转换、并发与异步协作 |
| 模块协作 | 通信协议、数据流和关键投递机制 |
| 技术决策 | 关键算法、重要技术选型、约束及选择原因 |

- AI 自主判断记录价值，以理解运行机制、维护核心数据、修改关键逻辑和后续扩展的长期需要为依据。
- 普通类、函数、局部变量、简单逻辑及临时实现细节无需记录。
- 按实际项目决定技术文档的拆分方式，同一主题集中维护。
- 区分已确定方案、待评估候选和已实现状态，避免将计划写成已完成。

### 模块映射

- 技术文档必须映射到开发者设计文档库中的模块。
- 模块名称必须保持一致，目录沿用开发者定义的模块名称。
- 每份文档写明所属模块，并链接对应开发者模块文档。
- 涉及多个模块时列出全部关联模块，统一放入 `跨模块设计/`，正文集中维护。
- 跨模块文档逐一链接对应开发者模块文档，相关模块文档通过链接回指技术设计。
- 禁止自行建立另一套模块体系。模块尚未确定时明确标记待定关系，不能伪造已确认映射。
- 删除、合并或更名模块时，同步调整技术文档归属、目录、引用及索引。

例如，开发者规定多设备连接、独立状态和断线重连。AI 自主决定设备数据结构、状态机、重连机制和异步协作，并将关键方案记录在对应模块下。

新建或重整技术文档时可参考[AI 设计记录模板](assets/ai-design-template.md)，单模块与跨模块设计按实际情况选择归属信息。

## 当前设计与重要变更

- 正文始终描述当前有效设计。替代方案退出当前正文，必要取舍保留在变更原因中。
- 重要变化在对应文档内记录编号、概览及原因，可附日期、影响模块和 Git Commit。
- 同步更新受影响的设计、模块映射和索引。
- 变更编号在文档内保持稳定，可用 `CHG-001`。跨文档引用同时带文档路径，避免编号歧义。
- 实际提交时尽可能在 Git Commit 中引用文档路径和变更编号；只有已存在的提交才填写哈希或链接。
- Git 保存完整历史和 Diff。无需另建全局变更记录，也无需在正文复制旧版设计。

| 需要重要变更记录 | 无需重要变更记录 |
| --- | --- |
| 模块职责调整、拆分或合并 | 普通文档整理及文字编辑 |
| 核心数据结构或数据库结构变化 | 普通 UI、文字、颜色或按钮位置调整 |
| 关键业务时序、通信机制变化 | 不影响设计的代码重构及 Bug 修复 |

## 内容与一致性

- 使用用户当前语言，短句、列表和表格优先，避免长段落。
- 两套文档的目标、约束、接口和行为保持一致，技术方案不能替代已确定的设计要求。
- 用相对链接连接本地文档，在线文档使用实际页面链接。
- 保持索引、模块名称、归属和双向引用可达且准确。
- 描述当前实现或验证结果时以代码及实际执行结果为依据。
- 模板仅提供内容组织参考，删除不适用章节和提示，避免为了形式创建文件。
